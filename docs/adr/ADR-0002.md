# ADR-0002. Спосіб маршрутизації зовнішніх запитів через Ocelot API Gateway

## Статус
Accepted (2026-09-09)

## Контекст
У рамках реалізації стратегії поступової міграції (патерн Strangler Fig) від модульного моноліту (`src/Monolith`, порт `5100`) до цільових мікросервісів (`Auth`, `Catalog & Products`, `Orders`) виникла потреба організувати єдину точку входу (Single Point of Entry) для зовнішніх клієнтів (веб-SPA, мобільні додатки, інтеграційні системи).

Без проміжного шлюзу клієнти змушені знати топологію внутрішньої мережі, хости та порти окремих сервісів, що призведе до порушення інкапсуляції та потреби переписувати фронтенд при кожному винесенні модуля в окремий процес. Також постала потреба у централізованому наскрізному логуванні, обробці CORS та генерації наскрізного ідентифікатора запиту (`X-Correlation-Id`).

## Розглянуті варіанти

### 1. Пряма взаємодія без шлюзу (Direct Client-to-Service Architecture)
- **Опис**: Клієнт звертається безпосередньо до кожного сервісу за його індивідуальною адресою та портом (`:5100` для моноліту, `:5101` для Auth, `:5102` для Catalog, `:5103` для Orders).
- **Плюси**:
  - Відсутність додаткового мережевого посередника та нульова затримка на проксіювання.
  - Простіша топологія на початковому етапі розробки (менше запущених процесів).
- **Мінуси**:
  - Розкриття внутрішньої топології та структури портів клієнту.
  - Будь-яка зміна маршрутизації чи винесення сервісу вимагає змін у коді клієнтського застосунку.
  - Необхідність дублювання налаштувань CORS, автентифікації та логування в кожному сервісі окремо.

### 2. Ocelot API Gateway
- **Опис**: Спеціалізований та легкий шлюз для платформи ASP.NET Core, у якому вся логіка маршрутизації та обробки запитів конфігурується декларативно через JSON-файл (`ocelot.json`).
- **Плюси**:
  - Декларативна модель конфігурації маршрутів (`UpstreamPathTemplate` / `DownstreamPathTemplate`) без написання надлишкового C# коду.
  - Зміна напрямку запитів (перемикання з моноліту на новий сервіс) виконується простою зміною одного параметра в конфігураційному файлі без перекомпільовування шлюзу.
  - Підтримка маршрутів-перехоплювачів (catch-all `/api/{everything}`) та пріоритетної маршрутизації (specific routes over catch-all).
  - Нативна інтеграція з ASP.NET Core middleware (CORS, кастомні health checks, middleware логування та Correlation ID).
- **Мінуси**:
  - Дещо менша пікова пропускна здатність на екстремальних навантаженнях порівняно з низькорівневим рушієм YARP.
  - Термінальний характер `UseOcelot()`, що вимагає реєстрації всіх власних ендпоінтів (`/health`) строго до виклику шлюзу.

### 3. YARP (Yet Another Reverse Proxy від Microsoft)
- **Опис**: Низькорівневий, високопродуктивний зворотний проксі від команди Microsoft, оптимізований для маршрутизації величезних обсягів сирого HTTP-трафіку.
- **Плюси**:
  - Максимальна швидкість обробки мережевих пакетів, мінімальне використання оперативної пам'яті.
  - Гнучка програмна конфігурація та підтримка розширеного кластерингу.
- **Мінуси**:
  - Орієнтований на низькорівневий проксінг, а не на роль шлюзу API: вимагає значно більше коду C# для маніпуляцій із маршрутами та заголовками.
  - Складніша конфігурація для швидкої реалізації патерну Strangler Fig у навчальному проєкті.

### 4. Хмарний керований шлюз (AWS API Gateway, Azure API Management, Kong Gateway)
- **Опис**: Повністю керовані хмарні сервіси маршрутизації та керування API.
- **Плюси**:
  - Вбудоване автоматичне масштабування, DDoS-захист, готові дашборди моніторингу та білінгу.
- **Мінуси**:
  - Жорстка прив'язка до провайдера (vendor lock-in).
  - Складність або повна неможливість локального офлайн-запуску на машині розробника без підключення до платної хмари.

## Рішення
Для нашого проєкту обрано **Ocelot (Варіант 2)** як центральний API Gateway на фіксованому порті `5000`:
1. Усі клієнтські запити надсилаються на єдиний хост `http://localhost:5000`.
2. Конфігурація маршрутів винесена у `ocelot.json`, де першими зафіксовані явні маршрути для модулів, які мігруватимуть першими (`/api/auth/{everything}` та `/api/categories/{everything}`), а останнім визначено загальний перехоплювач `/api/{everything}` на моноліт (`http://localhost:5100`).
3. Додано middleware для генерації та прокидання наскрізного ідентифікатора `X-Correlation-Id` для забезпечення відстеження запитів (Distributed Tracing).
4. Зареєстровано ізольований ендпоінт `/health` до виклику термінального `UseOcelot()`.

## Наслідки

### Позитивні наслідки:
- **Інкапсуляція топології**: Клієнт взаємодіє виключно з портом `5000`. Внутрішній порт моноліту (`5100`) або майбутніх сервісів (`5101`, `5102`, `5103`) повністю приховані.
- **Безшовна заміна компонентів (Strangler Fig)**: Під час винесення `Auth Service` чи `Catalog Service` у наступних лабораторних роботах клієнтський код не змінюється — змінюється лише значення `DownstreamHostAndPorts` у відповідному маршруті `ocelot.json`.
- **Централізовані наскрізні задачі**: CORS, генерація correlation id та базове логування затримок обробляються в одній точці.

### Негативні наслідки та компроміси:
- **Додатковий мережевий стрибок (Network Hop Overhead)**: Проходження запиту через шлюз додає від 2 до 5 мс затримки до кожного HTTP-запиту.
- **Єдина точка відмови (Single Point of Failure - SPOF)**: У разі аварійного завершення шлюзу зовнішні клієнти втрачають доступ до всієї системи, що в продуктивному середовищі вимагатиме горизонтального кластерингу з балансувальником (наприклад, NGINX або HAProxy).
- **Додатковий застосунок в інфраструктурі**: Необхідність підтримки, конфігурації та моніторингу ще одного окремого процесу в рішенні.
