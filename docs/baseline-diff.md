# Порівняння поведінки API замовлень: Моноліт (Baseline) vs OrderingService

## Огляд
Згідно з вимогами ЛР2 було виконано зняття еталонних відбитків запитів та відповідей (baseline) для монолітного сервісу (`src/Monolith`, порт `5100`) за 10 ключовими сценаріями (збережено у `tests/baseline/`).
Після реалізації мікросервісу `OrderingService` (порт `5003`) та перемикання маршрутів на API Gateway (`http://localhost:5000/api/orders`) проведено детальне порівняння структури тіла, кодів відповідей та заголовків.

## Порівняльна таблиця сценаріїв

| № | Сценарій | Було (Моноліт :5100) | Стало (OrderingService :5003) | Чи є різниця | Обґрунтування різниці |
|---|---|---|---|:---:|---|
| 1 | **Створення з коректними даними** | `201 Created`<br/>Location: `/api/orders/{id}`<br/>JSON: `id`, `orderNumber`, `userId`, `status`, `totalAmount`, `createdAtUtc`, `items` | `201 Created`<br/>Location: `/api/orders/{id}`<br/>JSON: `id`, `orderNumber`, `userId`, `status`, `totalAmount`, `createdAtUtc`, `items` | **Ні** | Повний збіг контракту, полів та заголовка `Location`. Товар перевірено по gRPC. |
| 2 | **Створення без токена** | `401 Unauthorized`<br/>Порожнє тіло, заголовок `WWW-Authenticate: Bearer` | `401 Unauthorized`<br/>Порожнє тіло, заголовок `WWW-Authenticate: Bearer` | **Ні** | Захист не змінився, анонімні запити відхиляються на рівні JWT-автентифікації. |
| 3 | **Створення з неіснуючим ItemId** | `404 Not Found`<br/>ProblemDetails: `title="Not Found"`, `status=404` | `404 Not Found`<br/>ProblemDetails: `title="Not Found"`, `status=404` | **Ні** | `RpcException(StatusCode.NotFound)` від `CatalogService` транслюється в ідентичний `404 ProblemDetails`. |
| 4 | **Порушення бізнес-правил (кількість ≤ 0 або недостатній залишок)** | `400 Bad Request` (FluentValidation) або `409 Conflict` (перевищення залишку) | `400 Bad Request` (FluentValidation) або `409 Conflict` (перевищення залишку) | **Ні** | Збережено всі правила валідації запиту та перевірки складського залишку через gRPC. |
| 5 | **Повтор запиту з тим самим Idempotency-Key** | `201 Created` / `200 OK`<br/>Повертається раніше створений об'єкт | `201 Created` / `200 OK`<br/>Повертається раніше створений об'єкт | **Ні** | Захист від дублювання працює ідентично; повторний запит не створює друге замовлення в базі. |
| 6 | **Отримання свого замовлення за ID** | `200 OK`<br/>Повний JSON замовлення з масивом позицій | `200 OK`<br/>Повний JSON замовлення з масивом позицій | **Ні** | Поля, типи та формат дати UTC повністю відповідають вихідному API. |
| 7 | **Спроба отримати чуже замовлення** | `404 Not Found`<br/>ProblemDetails | `404 Not Found`<br/>ProblemDetails | **Ні** | Принцип безпеки дотримано: для чужого замовлення повертається 404 замість 403, щоб не розкривати його існування. |
| 8 | **Скасування замовлення (`POST /api/orders/{id}/cancel`)** | `200 OK`<br/>Статус: `Cancelled`<br/>Повторне скасування: `409 Conflict` | `200 OK`<br/>Статус: `Cancelled`<br/>Повторне скасування: `409 Conflict` | **Ні** | Статус змінюється, повторні спроби скасувати вже скасоване замовлення блокуються. |
| 9 | **CatalogService недоступний** | `503 Service Unavailable`<br/>ProblemDetails, заголовок `Retry-After: 5` | `503 Service Unavailable`<br/>ProblemDetails, заголовок `Retry-After: 5` | **Ні** | Сервіс не аварійно падає з 500, а повертає детерміновану відповідь 503 при мережевих збоях каталогу. |
| 10 | **Список замовлень користувача** | `200 OK`<br/>Масив замовлень, сортування за `createdAtUtc DESC` | `200 OK`<br/>Масив замовлень, сортування за `createdAtUtc DESC` | **Ні** | Збережено сортування від найновіших до найстаріших та повний склад позицій. |

## Висновок
Регресій або непередбачених відхилень у поведінці не виявлено. Після перемикання маршруту в `ocelot.json` клієнтські програми продовжують працювати без внесення будь-яких змін до клієнтського коду.
